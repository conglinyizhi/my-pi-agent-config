# 出题示例（正确案例）

15 道单选题，来自 Benchmark 概念讨论的复盘修正版。展示「洗牌后」的成品形态：
- 干扰项与正确答案等长、等具体、同样可信，只差一个细节/关系
- description 只做中性补充（术语解释/背景），不给对错线索
- 答案位置（A-D）由 `scripts/shuffle-quiz-options.mjs` 洗牌生成，每次运行结果不同；使用时不照抄位置，位置永远交给脚本

读法：带 ✓ 的是正确项，先遮住它自测一遍，再看选项设计好在哪。

> 题型说明：这批题出自旧标准，其中 **Q1、Q6、Q12 偏记忆型**（术语名/细节/比喻原文），新标准下不作为出题方向参考；其余为概念型。全部题目仍可参考**选项写法**（干扰项迷惑度、中性 description）。

## Q1. 同类型的题目放在一起组成一个测试集，这个测试集叫什么？

- **A.** Benchmark ✓
  - 说明：用来统一衡量模型能力的测试集合
- **B.** Prompt Set
  - 说明：提示词模板的集合
- **C.** Corpus
  - 说明：大规模文本语料的统称
- **D.** Training Set
  - 说明：模型训练阶段使用的数据

## Q2. 为什么评测一个模型不能用几道题，而要几千几万道？

- **A.** 官方想显得自己工作量充足，更有面子
  - 说明：与评测原理无关
- **B.** 题太少无法代表模型真实能力，结果不具统计意义 ✓
  - 说明：样本量影响结果可靠性
- **C.** 题少了程序没法判分，格式解析不出来
  - 说明：程序判分依赖固定格式解析
- **D.** 题目越多评测跑得越快，效率更高
  - 说明：评测耗时与题量成正比

## Q3. MMLU Pro 这类选择题 benchmark 是怎么判分的？

- **A.** 提示词强格式引导，答案放固定位置，程序读取比对 ✓
  - 说明：答案格式可程序化解析
- **B.** 用另一个大模型逐题判断对错
  - 说明：开放题常用的判分思路
- **C.** 请人工阅卷员逐题对照评分
  - 说明：题量太大，人工不现实
- **D.** 跑测试用例看通过率
  - 说明：代码题常用的判分方式

## Q4. 有些测试题前面有一大长串内容，这串内容是什么？

- **A.** 评测用的干扰信息，对分数没有影响
  - 说明：评测提示词的一部分
- **B.** 评分模型用来判分的提示词
  - 说明：这是给裁判看的
- **C.** 供模型参考的正确答案提示
  - 说明：评测时模型看不到标准答案
- **D.** 正式回答前的参考示例，给示例时分数通常会更高 ✓
  - 说明：示例数量可在评测框架中配置

## Q5. 分数表里 pass@1 和 pass@5 的区别是什么？

- **A.** pass@1 和 pass@5 是同一指标的不同写法
  - 说明：两种写法的口径不同
- **B.** pass@1 只做第一题，pass@5 做五道题
  - 说明：与题目数量无关
- **C.** pass@5 要求生成 5 次且 5 次全对才算对
  - 说明：比 pass@1 更严格
- **D.** pass@5 是生成 5 次答案，采样出一次对的就算对 ✓
  - 说明：采样次数越多越容易碰对

## Q6. HLE（人类的最后一次考试）的题目是怎么收集的？

- **A.** 从历年高考和学科竞赛真题中筛选整理
  - 说明：公开考试题来源
- **B.** 找外包团队从公开网络资料批量搜刮题目
  - 说明：部分测试集确实这么收集
- **C.** 全球专家为争夺固定奖金池出题，新题须让主流模型准确率接近随机 ✓
  - 说明：奖金池驱动，难倒模型才算数
- **D.** 让平台用户投票选出模型答不出的题
  - 说明：众包式选题

## Q7. HLE 为什么需要动用另一个大模型来判断对错？

- **A.** 人工判分的成本太高，划不来
  - 说明：成本不是主因
- **B.** 题目全是诗歌和文章这类开放题
  - 说明：HLE 以推理题为主
- **C.** 答案形式复杂难以程序比对，需要 LLM 当裁判 ✓
  - 说明：评分模型和提示词会影响分数
- **D.** 题目本身没有标准答案，无法比对
  - 说明：HLE 有标准答案

## Q8. SWE-bench（修真实 GitHub issue）的测试用例分成 fail-to-pass 和 pass-to-pass，分别指什么？

- **A.** fail-to-pass 是新增的回归测试；pass-to-pass 是原有的单元测试
  - 说明：不是按新旧划分
- **B.** fail-to-pass 是修复前就通过的用例；pass-to-pass 是修复后新通过的用例
  - 说明：两组用例的先后关系相反
- **C.** fail-to-pass 是修复后从失败变成功的用例；pass-to-pass 是修复前就通过、修复后仍需通过的用例 ✓
  - 说明：一测修复效果，二测防回归
- **D.** fail-to-pass 衡量修复是否生效；pass-to-pass 衡量测试集本身是否有效
  - 说明：第二项考察对象不同

## Q9. Chatbot Arena（大模型盲测网）是怎么给模型打分的？

- **A.** 用标准答案逐题比对判分
  - 说明：Arena 没有标准答案
- **B.** 跑测试用例统计通过率
  - 说明：这不是投票型榜单
- **C.** 用户把模型两两对比、盲测投票，用 ELO 机制算分 ✓
  - 说明：投票结果经 ELO 换算成排名分
- **D.** 邀请领域专家按多个维度打分
  - 说明：评委来自普通用户

## Q10. 写诗、写 HTML 这类没有固定答案的开放题，评测时怎么验证？

- **A.** 程序做字符串相似度比对判分
  - 说明：自然语言难以硬比对
- **B.** 用另一个大模型验证，必要时人工二次校验 ✓
  - 说明：LLM 当裁判，人工兜底
- **C.** 不验证，有输出就算得分
  - 说明：那分数就失去区分度
- **D.** 让用户投票决定是否得分
  - 说明：投票是另一类榜单的路子

## Q11. 对比两个模型的跑分时，最重要的是什么？

- **A.** 对比模型的参数量和训练数据规模，越大越强
  - 说明：参数量不决定跑分可比性
- **B.** 参考社交平台上真实用户的使用感受，一票否决
  - 说明：主观感受与跑分是两回事
- **C.** 直接看官方宣传海报上的总分排名，相信官方口径
  - 说明：小字里的设置常被忽略
- **D.** 确认 few-shot 数量、pass@k、思考模式、工具、评分模型等设置一致 ✓
  - 说明：基准不对齐，差距无意义

## Q12. 测评时设置 thinking 模式的「努力程度 / 最大 token 预算」，最像什么？

- **A.** 给考生限定答题时间和草稿纸数量 ✓
  - 说明：限制的是思考投入
- **B.** 决定考生要考几门科目
  - 说明：科目是考察范围
- **C.** 决定监考老师的严格程度
  - 说明：监考不改变作答投入
- **D.** 决定试卷的总体难度
  - 说明：难度是题目属性

## Q13. SWE-bench 马拉松这类长任务排行榜，为什么要同时标注模型和 agent 脚手架？

- **A.** 为了让榜单在形式上显得更专业
  - 说明：有实际技术原因
- **B.** 脚手架是榜单唯一的评分标准
  - 说明：模型仍然重要
- **C.** 模型本身的差异已经不重要
  - 说明：模型是核心变量之一
- **D.** 模型与脚手架共同决定结果，耗时和 token 消耗也影响解读 ✓
  - 说明：同一模型配不同脚手架差异很大

## Q14. 「跑分没输过，一用就拉垮」的割裂感，主要原因是什么？

- **A.** 评测环境网络条件好，真实使用网络条件差
  - 说明：与网络条件无关
- **B.** 真实任务多无标准答案，benchmark 覆盖不到；刷分过拟合还损害真实能力 ✓
  - 说明：标准答案型测试与真实世界脱节
- **C.** 用户没有掌握正确的提示词写法，问法不对
  - 说明：不是用户用法问题
- **D.** 模型在评测时故意隐藏实力，实际用起来才发力
  - 说明：模型没有主观故意

## Q15. 榜单的意义在降低，主要原因是什么？

- **A.** 评分模型能力太弱，判分结果不准
  - 说明：判分精度不是主因
- **B.** 测试题难度过高，没有模型能考出好成绩
  - 说明：难度不是失效原因
- **C.** 模型能力超出测试题能考察的范围，跑分也难代表真实环境水平 ✓
  - 说明：学生超过老师，老师出不了卷
- **D.** 现有榜单数量太少，缺乏足够的横向参照
  - 说明：榜单数量反而越来越多
