# 审核流 SDK（设计稿）

> 结论先摆：这不是从零造流程引擎，而是把已有的审核链**抽成节点**、把连线**挪出代码**。
> 第一版只做 SDK + 文本流程 + 逐节点轨迹（只读）。可视化编辑留到轨迹证明有用之后。

## 0. 你定的四件事

| 你的选择 | 落成什么 |
|---|---|
| 痛点要三条都治，最烦改完看不清效果 | 轨迹（trace）是一等公民，不是附加功能 |
| 引擎打包成 SDK，PTC / bash 只是变量 | 入口是 RunFlow(flowId, input)，场景由输入决定，不由代码分支决定 |
| 可视化编辑太费劲，先把文本做出来；只读的运行图就够 | v1 不做编辑器；轨迹要能回答卡在哪个节点、为什么 |
| 执行语义节点级可配、兜底写在流程里 | 节点自带并发与预算；失败分支是图的一部分 |

## 0.1 一个具体的动机样本（提督 2026-10-05 给的实例）

一次真实审核里出现过这样的组合：

```
云端模型审核  ⚠️ 有风险   1 个维度，1 项越线
  整体可疑：置信度 0.00 < 0.5（模型没把握）
对话模型意见  ✅ 安全
  仅编辑计划文档并且只读 grep，路径明确

分类模型权重
  整体可疑  [====] 0.50  置信 0.00   > 0.50
```

- **现象**：分类模型自己写着「模型没把握」（置信 0.00），那一维照样算一项越线，结论被抬成「有风险」；
  同时对话模型判的是安全。两条结论打架，人就得额外花注意力去分辨"到底要不要紧"
- **现在为什么治不了**：维度越线只看风险值与阈值，**没看置信**；合并又是写死的「任一判风险就弹窗」，
  没有「弃权」这个概念——所以一个自己都没把握的判断，和一条笃定的判断，在合并处是等权的
- **SDK 里该怎么表达**：
  - `classifier` 节点输出结构化维度（值 / 置信 / 是否越线），不再只给一个笼统的结论
  - `merge` 节点支持**弃权门限**：置信低于 ε 的维度视为弃权，不计越线、不抬结论（ε 是数据，不是代码里的 if）
  - 弃权必须进轨迹：「这一维被忽略了，因为置信 0.00 < 0.20」——否则人会怀疑是漏看了
  - 哪几个维度免疫这条规则、ε 取多少，属于要反复试的参数——这正是低代码该省下来的地方
- **不单独修**（提督 2026-10-05 的判断）：这一条单独打补丁用处有限，等统一改脚本时一起改更快。
  真要动手前先查清 0 置信是从哪条路进来的（分类器返回、还是解析兜底），别把「解析失败」误当成「模型没把握」

## 1. 三层边界

```
┌─ 节点库（SDK）    事实层 / 规则 / 分类模型 / 对话模型 / 干跑 / 人工闸门 / 自动放行 / 合并
│  每个节点：Run(ctx, input) → output + 一条轨迹记录
├─ 流程运行器        并发、预算、取消、合并、失败分支、缓存、轨迹
└─ 流程的表示        ① TS 模块（v1）  ② 声明式文件（v1.5）  ③ 可视化编辑器（v3）
```

三个表示**共用同一个运行器**：声明式与图形只是在生成同一张节点图。
没有这条约束，就会出现两套语义各自跑偏——这是这个项目最容易翻车的地方。

## 2. 节点清单（全部是已有能力的搬运）

| 节点 | 现在长在哪 | 输入 | 输出 |
|---|---|---|---|
| facts 事实层 | preshell --spec 输出（lib/preshell.ts） | 命令 / 脚本 | 结构化事实 + 可信度 |
| rule 规则匹配 | findHighlights 那套 token 规则 | 文本 + 规则表 | 命中列表 |
| scan 静态扫描 | lib/ptc-analyze.ts | 脚本原文 | 工具面 / 路径 / 命令 / 看不清的地方 |
| dryrun 干跑 | lib/ptc-dryrun.ts | 脚本 | 预演调用序列 |
| classifier 分类模型 | extensions/sandbox-permissions/classifier-client.ts + review-dimensions.toml | 送审文本 + 维度阈值 | 每个维度的风险与依据 |
| chatreview 对话模型 | reviewCommand（llm-review.ts） | 送审文本 + 工具说明 | verdict + 理由 + 建议 |
| merge 合并 | backend=chain 那段（任一判风险就弹窗） | 若干结论 | 合并结论 |
| gate 人工闸门 | lib/approval-channel.ts 的文件协议 | 结论 + 事实 + 轨迹 | 人的决定（含附言） |
| autoapprove 自动放行 | mode=auto 判据（唯一实现在 preReviewBashCommand / preReviewPtcScript） | 结论 + 档位 | 放行 / 不表态 |
| terminal 出口 | 各链的返回 | 决定 | allow / deny / 转人工 |

节点种类就这十来个，而且每个都已经有实现、有测试。**抽节点的工作量在接口统一，不在重写。**

## 3. 节点级执行语义

每个节点自己声明：

```
mode        serial | parallel | cascade
  serial    等上游结论再决定跑不跑（省调用，慢在关键路径）
  parallel  与同组节点同时开跑（快，调用多）
  cascade   便宜的先跑，判不出来才升级（最坏情况更慢）
budget      只算两样（提督 2026-10-05 定的口径）：
              calls  模型调用次数上限，默认 5（现状 3 次乘 1.5 向上取整）
              cost   token / 费用上限，默认不限
              用尽就走 onBudget
deadline    整次运行的硬上限 60 秒：超了就是这次审计脚本失败，走 fail 出口
            （网络与单模型的超时**不算预算**——那是各家模型自己的设置，留给用户自己折腾）
onEmpty     拿不到结论时交给谁（默认交给失败分支）
onBudget    预算用尽时交给谁（默认接流程的 fail 出口）
```

合并策略在 merge 节点上选：谁先回 / 投票 / 取最严 / 一致才通过。现在的 chain 就是「取最严」，把它显式化成 merge 的一个参数，行为不变。

## 4. 失败路径与兜底

你选了「流程里自己写」，于是兜底不是引擎的隐含行为，而是**图上的一条边**：

- 每个节点有 `onError` 与 `onTimeout` 两个出口，不接就是**走该流程的 fail 出口**
- 流程必须静态可验：每个节点都能到达一个 terminal，否则加载即报错（不等到运行）
- 默认 fail 出口 = 拒绝。**要放行必须在图上显式写出来**，这是审核面的底线

这样那条一直挂着的问题（分类模型超时怎么办）就变成每条流自己的一行配置，而不是全局策略。

## 5. 轨迹（这是你最想要的那块）

一次运行 = 一串节点记录：

```
nodeId / nodeKind / 开始与结束时刻 / 结论（含 verdict 与理由）
输入摘要（送审了什么、多长、哪些维度不适用）/ 输出摘要
模型、耗时、token、是否命中缓存
走到这个节点的原因（哪条边进来的）/ 从哪条边出去
```

窗口里要回答两个问题，别的都是装饰：

1. **卡在哪**：哪个节点判了 risky/dangerous、哪个节点没判出来（超时/报错）、哪条失败边被走到
2. **为什么是这个结论**：该节点的理由原文 + 它依据的事实（规则命中 / 维度权重 / 模型原话）

闸门窗口现在的「云端模型审核」「风险维度」两块正好是这条轨迹的尾巴，扩成完整链路即可。
轨迹沿用现在的策略：内存滚动、不主动落盘。

## 6. 可测性（不做这条就别做这个项目）

- 运行器是纯函数：输入（图 + 事件 + 假节点实现）→ 输出（决定 + 轨迹）
- 假节点：fixedVerdict(safe)、failing(timeout)、slow(200ms) 之类，测试里替换真模型
- 迁移即等价：新流程跑一遍旧链路，**同为输入时必须给出同一个决定**；这条做成回归用例
  （现有 bash / PTC 两套用例直接拿来当基线）

## 7. 流程的第一版表示：TS 模块（已定）

你说了「引擎打包成 SDK 然后在里面写代码，或者写低代码来跑」——这两种其实是同一个东西的两个前端。
v1 先要 TS 模块，理由是它能被 tsc 检查、能被单测、能直接调假节点：

```ts
// flows/bash.ts
export const bashFlow: Flow = {
  id: "bash",
  deadlineMs: 60_000,        // 整次运行的硬上限：超了就是审计脚本失败
  budget: { calls: 5 },      // 只算调用次数与费用；单模型超时是模型自己的设置
  nodes: [
    { id: "facts", kind: "facts", mode: "serial" },
    { id: "rule", kind: "rule", after: ["facts"] },
    { id: "classify", kind: "classifier", mode: "parallel", settings: { timeoutMs: 3000 }, after: ["facts"] },
    { id: "chat", kind: "chatreview", mode: "parallel", settings: { timeoutMs: 30000 }, after: ["facts"] },
    { id: "merge", kind: "merge", strategy: "strictest", after: ["classify", "chat", "rule"] },
    { id: "gate", kind: "gate", after: ["merge"] },
    { id: "auto", kind: "autoapprove", mode: "auto", after: ["merge", "gate"] },
  ],
  onError: "deny",
};
```

声明式文件（TOML 或 JSON）在 v1.5 补上，专门服务于将来的可视化编辑器；
两者共用运行器与校验器，声明式只是把上面这段读进来。

## 8. 分期

| 期 | 内容 | 做完能回答什么 |
|---|---|---|
| v1 | 节点库抽取 + 运行器 + TS 流程 + 轨迹数据；bash 链等价迁移 | 换模型/换顺序不改引擎代码；回归全绿 |
| v2 | 闸门窗口渲染完整轨迹（只读链路图 + 卡点高亮） | 一眼看出卡在哪、为什么 |
| v3 | 声明式流程文件 + PTC 流 | 场景只是变量这件事成立 |
| v4 | 可视化编辑 | 只有前三期天天在用、还嫌改文本麻烦时才做 |

## 9. 硬约束（写进代码注释，不靠自觉）

1. 模型节点**不授予权限**：只有 gate（人）与 autoapprove（显式判据）能放行
2. 没有 terminal 可达的流程**加载即失败**，不许静默挂住
3. 默认 fail = 拒绝；放行必须显式写在图上
4. 声明式与图形表示必须生成同一张图（单一运行器），否则不许上
5. 轨迹必须包含每个走到过的节点，包括被跳过与失败的；**跳过的原因也要记**

## 10. 风险与反悔点

| 风险 | 反悔点（到这一步就退） |
|---|---|
| 抽象泄漏：节点接口塞不下某个既有能力的怪癖 | v1 抽取时若被迫给节点加特例分支，就先停手重画接口 |
| 轨迹没人看 | v2 做完后一周内没主动打开过轨迹窗，说明真正缺的不是它 |
| 两套语义并存（旧配置 + 新流程） | 迁移期内允许，但 v3 结束必须删掉旧支路 |
| 声明式文件写起来比 TS 还啰嗦 | 若 TOML 版本需要比 TS 多写三成内容，就只留 TS + 可视化 |

## 11. 已定的与还挂着的（提督 2026-10-05）

已定：

1. **TS 优先**：流程与节点都用 TypeScript。后期开放 SDK 时别人好上手、编辑器提示全、
   交给 AI 改也更容易读懂，这些比声明式文件的优势更值钱
2. **轨迹导出成 .ts**：不是导出 JSON 日志，而是固化成一条可回归的用例（输入 + 各节点结论 + 最终决定），
   能直接进测试集重放（一条夹具 = 一条可回归用例）
3. **转人工的次数上限不写进引擎**，写进设计规范；超过阈值警告用户，不做硬性拦截

还挂着：

1. 每流预算的默认值（四个维度见第 3 节）：新图默认沿用现状——calls 3、分类 3000ms、对话 30000ms、
   totalMs 45s、cost 暂不限
2. 轨迹内存滚动条数是否跟着 A/B 一起调
