# GUI 的 A/B 更新与故障回退（设计稿）

> 起因：狗粮式开发下，脚本里的问题只有跑起来才暴露；而 GUI 是唯一的图形操作面，它坏了就没地方操作。
> 加上你会周期性压缩 + reload 重启核心，于是「最新 GUI」与「正在跑的 pi」常常不是同一代，协议就有断层。
>
> 所以这份稿子要解决的不是「测得更细」，而是三件事：**候选先过金丝雀再上**、**坏了能立刻切回去**、
> **而切回去这条路本身不许依赖任何新代码**。

## 1. 现状（读到的）

| 项 | 现状 |
|---|---|
| 部署形态 | 单目录：bin/gui 直接指仓库里的 gui/electron，**没有版本槽** |
| 启动方 | lib/gui-runner.ts 的 findGuiBinary()，hub 与扩展都走它——只有这一处，好接管 |
| 文件协议 | `<window> <requestFile> <responseFile>`，前端挂载后写 `.ready`，提交写响应文件 |
| 已有的金丝雀雏形 | scripts/gui-fasttest.ts：并行起全部窗口，轮询 ready/error，自动判定，30s 超时 |
| 崩溃感知 | main.js 有 render-process-gone 处理；但没有现场保存（上周那次 SIGTRAP 只留了个 coredump） |
| 运行时目录 | ~/.pi/runtime 已在用（preshell 的 A/B 安装就在那儿）——GUI 的槽可以并排放 |

## 2. 两槽与原子切换

```
~/.pi/runtime/gui/<版本>/     实际产物（electron 目录 + 前端 dist）
~/.pi/runtime/gui/current  →  软链，指向上槽的那一个
~/.pi/runtime/gui/previous →  软链，指向上一个稳定版本
```

- **切换 = 换软链**（一条 mv），不依赖 Electron、不依赖 pi、不进任何新代码
- **回退 = 把 current 指回 previous 并杀掉候选进程**；这条路径做成一段独立 shell（脚本侧，不是扩展侧）
- 产物从哪来：显式打包脚本把仓库构建结果落到新版本目录，而不是直接部署工作区（可复现、可回退）
- 不做：增量更新、签名校验（单用户机器）；但记一条——不跑来历不明的产物

## 3. 上槽门槛：连续 N 次干净往返（累积信心，不是一次性金丝雀）

提督 2026-10-05 定的口径：**跑起来、正常收到请求，说明大致稳定；连续五六次到七八次都稳，
才认为这个版本可替换。**

一次「干净」的往返 = 四件事同时成立：

1. 窗口起来，`.ready` 写出（前端挂载了）——这只是**早期信号**，不作数
2. 真实请求进来了，走完整条链
3. **以最终审核结果为准**：人给出了结论（允许/拒绝/附言），响应文件正常写出
4. 中途没崩（无 render-process-gone）、没超时、**没人叉掉窗口**

第 4 条里的「叉掉」按提督的约定算**错误信号**：对结果不满意就直接关掉窗口，
这等于投了一张反对票。所以「关窗且没写响应文件」= 失败，而不是「用户没意见」。

门槛：连续 N 次干净（默认 6，可配）。任一次失败**清零重来**，并把失败现场存下来（见第 6 节）。

失败处理：不自动上槽、不自动重试；候选目录与日志原样留着。
**允许 `--force` 强行上槽，但必须留痕**：记一条「谁在什么时候强推的」，方便事后对上。

## 4. 协议断层（能力探测，不比版本号）

起因是周期性的压缩 + reload：核心重启后可能与 GUI 差一代。
**不匹配时在 pi 的 TUI 界面打印一行**让用户知道（走 pi 的通知/状态输出，不是往控制台打 log）。

- GUI 启动时**自报能力**：支持的窗口清单 + 关键字段形态，一行 JSON（preshell 的 --spec 已经是这个路子，直接抄）
- pi 侧拿它查自己需要的能力：缺了就降级（没有 review 窗口就别给那个命令；已有先例 notPorted()）
- GUI 侧对未知字段忽略、缺字段给默认（init-data.js 现在就是「缺就不渲染」，继续）
- 兼容窗口：GUI 至少兼容上一代请求形状；**破坏性字段变更才 bump 协议号，且只提示不拦**

## 5. 运行期崩溃：自动回退 + 通知（已定）

金丝雀管的是「上槽前」，这一节管「上槽之后」：

- 看门狗发现窗口进程崩了（异常退出、render-process-gone、连续无响应）→ 把 current 软链指回 previous，
  杀掉残留进程，然后**通知提督一次**（hub/IM 一句话，带上崩的是哪个版本、现场在哪）
- 自动回退不改任何代码路径：它执行的就是第 2 节那段独立 shell
- 回退后候选的连续成功计数清零，且记入现场留档

## 6. 极端情况下的图形操作面（三层，从近到远）

1. **软链切回上一个稳定版本**——一段几十行的独立 shell，Electron 完全起不来时也能用
2. **TUI 兜底**——闸门已有 TUI 面板（不依赖 GUI 进程）
3. **IM 通道**——飞书适配器，本机闸门窗答不了时它接手

关键在第 1 层：它必须在「Electron 崩了」这个前提下可用，所以它不能住在 Electron 里，也不能住在 pi 扩展里。

## 7. 崩溃现场

候选失败时把这几样存到状态目录（按敏感内容对待，不进仓）：

- 当时的 request.json（能复现就有救）
- stderr / 退出码 / render-process-gone 详情
- 若是核心转储，记一条提示（coredump 路径）

## 8. 本稿范围之外

GUI 侧没有网络请求：文件协议、IPC、spawn 全在本地。所以「注入网络故障」这件事与本稿无关。

（审核链那边确实会调模型走 HTTP，但那是脚本侧的事，不在这里混着做。）

## 9. 分期

| 期 | 内容 | 完成标志 |
|---|---|---|
| 1 | 两槽 + 软链切换 + 独立回退脚本 | 手动换一次版本再切回来，全程不碰 Electron |
| 2 | 干净往返计数 + 上槽门槛（连续 N 次）+ --force 留痕 | 故意塞一个坏产物跑，计数永不达标、它拒绝上槽 |
| 2.5 | 运行期看门狗：崩了自动回退并通知 | 人为崩一次，软链指回去且收到提示 |
| 3 | 能力探测 + 缺能力降级 | 旧 GUI 配新 pi 跑通一次 |
| 4 | 崩溃现场保存 | 人为崩一次，日志与请求快照都落对地方 |


## 10. 硬约束

1. 切换与回退不依赖被切换的东西（软链 + 独立 shell）
2. 金丝雀失败绝不自动上槽、绝不自动重试
3. 协议不匹配只提示不拦——拦了就成了新的单点
4. 状态目录里的现场快照按敏感内容对待，不进仓

## 11. 还差你一句

1. **N 取多少**：5 / 6 / 7 都行，我默认按 6 写，计数与阈值都进配置
2. **产物怎么落**：我按「显式打包脚本」做（仓库构建结果落到 runtime 新版本目录），
   这样上槽前后都可复现；你要是想直接在 runtime 目录里构建，说一声
