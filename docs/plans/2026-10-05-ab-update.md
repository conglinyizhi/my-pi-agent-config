# GUI 与审核 SDK 的 A/B 更新与故障回退（设计稿）

> 起因：狗粮式开发下，脚本里的问题只有跑起来才暴露；而 GUI 是唯一的图形操作面，它坏了就没地方操作。
> 加上你会周期性压缩 + reload 重启核心，于是「最新 GUI」与「正在跑的 pi」常常不是同一代，协议就有断层。
>
> **状态：仍在计划阶段。除提督下令，不实施。** 原因：这个引擎本身还有维护性问题没想清，动它比动普通功能贵。
> **而切回去这条路本身不许依赖任何新代码**。

## 2. 槽位与原子切换

```
三个槽按角色命名，不按 ref 命名（提督 2026-10-05 定）：

~/.pi/runtime/<组件>/stable/   当前稳定版
~/.pi/runtime/<组件>/previous/ 上一个稳定版（回退目标）
~/.pi/runtime/<组件>/dev/      正在累积干净往返的候选
~/.pi/runtime/<组件>/head/     从当前 HEAD（或工作区）现构的一份，应急试跑用
~/.pi/runtime/<组件>/current → 软链，指向正在跑的那个（默认 dev）
~/.pi/runtime/<组件>/promote.log  晋升日志（jsonl：sha、时间、干净与否、谁推的）
每个槽里一份 manifest.json：{ ref, sha, dirty, builtAt, spec }

组件 = gui（窗口产物）| audit（审核 SDK 的实现：lib + extensions 的一份树）

**为什么要四槽**（提督 2026-10-05 问「达标之后自动切吗」带出来的）：只要允许自动晋升，
就必须多留一格 `previous` 接住被顶下来的 stable。否则自动晋升会把**回退目标本身**换掉——
第 6 次跑出问题时，你退回去的就是那个坏版本，等于把救生圈换成了坏掉的那个。
不加自动晋升的话三槽够；要自动就得四槽。

**tag 与槽是两件事**：tag 记「源码在哪一代」（仓里只有一个移动 tag stable），槽记「磁盘上跑哪一份」。
```

**产物算出来，不存进仓库。** 三种做法对比：

| 做法 | 判断 |
|---|---|
| 把构建产物提交进主仓 | ✗ 仓库已 gitignore 了 dist，提交进去自相矛盾；每次构建一条二进制 diff，历史与 review 全被污染 |
| 单独仓库 / submodule | ✗ 一个产品一条历史。submodule 带来游离 HEAD、嵌套提交、两边对不齐那套麻烦，收益是「两仓独立发版」——我们不需要 |
| **追 git ref 就地构建** | ✓ 源码本来就在仓里；仓里只多一个会移动的 tag |

- **仓库侧只多一个移动 tag**（标注 tag `stable`）指向被晋升的提交。**刻意只留一个**：两个 tag（stable + dev）会
  很自然地滑向 A/B/C 多路对比，那是另一件事，不是这套要解决的；不打不可变 tag，那会变成 tag 垃圾
- **组件有两个**：`gui`（窗口）与 `audit`（审核 SDK 的实现，即 lib + extensions 那一套）。
  两者同套机制、各自两槽，因为提督的判断是——审核这一侧崩了比 GUI 崩了更要命（一个卡住界面，一个卡住所有判断）
- **晋升** = `git archive <tag>` 取源码 → 构建到新槽 → manifest 记 `{ref, sha, dirty, builtAt, protocolSpec}` → 换 `current` 软链 → 往 `promote.log` 追加一条
- **回退不碰 git**：把 `current` 指回 `previous` 并杀掉候选进程。产物已在磁盘上，这条路做成一段独立 shell
  （脚本侧，不是扩展侧）。刻意不让回退依赖 git——狗粮期间 git 状态本身可能就是乱的
- **工作区脏时不晋升**：狗粮时候选多半来自正在改的工作区（还没提交），那种产物事后复现不出来。
  要求干净，脏就拒绝；要强推走 `--force`（与上槽那条同一个开关），manifest 里如实记 `dirty: true`
- 不做：增量更新、签名校验（单用户机器）；但记一条——不跑来历不明的产物

## 3. 上槽门槛：连续 N 次干净往返（累积信心，不是一次性金丝雀）

提督 2026-10-05 定的口径：**跑起来、正常收到请求，说明大致稳定；连续五六次到七八次都稳，
才认为这个版本可替换。**

一次「干净」的往返 = 四件事同时成立：

1. 窗口起来，`.ready` 写出（前端挂载了）——这只是**早期信号**，不作数
2. 真实请求进来了，走完整条链
3. **以最终审核结果为准**：人给出了结论（允许/拒绝/附言），响应文件正常写出
4. 中途没崩（无 render-process-gone）、没超时、**没人叉掉窗口**

第 4 条里的「叉掉」按提督的约定算**错误信号**：对结果不满意就直接关掉窗口，
这等于投了一张反对票。所以「关窗且没写响应文件」= 失败，而不是「用户没意见」。

门槛：连续 N 次干净，**N 默认 5**（提督 2026-10-05 定；计数与阈值都进配置）。
任一次失败**清零重来**，并把失败现场存下来（见第 7 节）。

失败处理：不自动上槽、不自动重试；候选目录与日志原样留着。
**允许 `--force` 强行上槽，但必须留痕**：记一条「谁在什么时候强推的」，方便事后对上。

### 达标之后自不自动切

两种都做，用配置选（默认自动）：

**自动晋升**（`auto_promote = true`）：第 N 次干净往返走完，那次动作结束后把 dev 升为 stable、
旧 stable 降为 previous、current 仍指 dev、计数清零。全程不需要人干预。三处边界：

1. **必须四槽**（见第 2 节）：没有 previous 接住，自动晋升会把回退目标一起换掉
2. **audit 侧只写软链**：真正生效要等下一次 reload——于是它**永远不会在会话中途把判定逻辑换掉**，
   这一点比 GUI 侧更安全（GUI 下一个窗口即生效，但有看门狗兜底）
3. **晋升要通知一句**（hub/IM 或 pi 的 TUI）：自动不等于无声，出了事得知道是从哪一次开始变的

**手动晋升**（`auto_promote = false`，或想提前切）：达标后只提示「候选已攒够 N 次，可以晋升」，
由人点一句。另外永远给 `--promote-now`——审计频率低的时候可能几周攒不到 N 次，
别让门槛变成卡住自己。

## 4. 协议断层（能力探测，不比版本号）

起因是周期性的压缩 + reload：核心重启后可能与 GUI 差一代。
**不匹配时在 pi 的 TUI 界面打印一行**让用户知道（走 pi 的通知/状态输出，不是往控制台打 log）。

- GUI 启动时**自报能力**：支持的窗口清单 + 关键字段形态，一行 JSON（preshell 的 --spec 已经是这个路子，直接抄）
- pi 侧拿它查自己需要的能力：缺了就降级（没有 review 窗口就别给那个命令；已有先例 notPorted()）
- GUI 侧对未知字段忽略、缺字段给默认（init-data.js 现在就是「缺就不渲染」，继续）
- 兼容窗口：GUI 至少兼容上一代请求形状；**破坏性字段变更才 bump 协议号，且只提示不拦**

## 4.5 audit 这个组件是什么，为什么它也要这套

pi 进程里跑着两份东西：

| | 是什么 | 崩了看得见吗 |
|---|---|---|
| gui | 窗口、渲染、把请求摆给人看——**只是脸** | 看得见（窗口没了） |
| audit | 真正做判断的那套：lib 里的 bash-approval / ptc-audit / approval-channel / preshell，扩展里的 sandbox-permissions / ptc | **看不见**——可能变成每次审计都超时、都拒绝，或者悄悄放行，而界面看着正常 |

所以 audit 也进这套机制。同套流程，三处不一样：

1. **槽里是一份树**：audit 槽 = 一份 lib/ + extensions/（构建时从 tag 取源码落进去，带 manifest）
2. **加载方式：仓库里的审核扩展变成一层薄壳**。壳里只写一句「去 ~/.pi/runtime/audit/current/ 加载真正的实现」，
   换槽 = 换软链，**pi 侧零配置改动**（alias 一行不碰，settings 也不碰）。
   为什么不用 --extension 指向槽目录：worker 是我们启动的，塞 flag 没问题；主会话是提督用 alias 启动的，
   往 alias 里加路径就成了「改起来散」。薄壳把这件事收进仓库内部。
   实现前必须先跑通的验证点：壳里动态 import 槽里的 .ts 是否可行；reload 时会不会重新取槽（要重新取才算换了）
3. **回退要重载**：扩展在启动时装载，所以换槽**必须配一次 reload/重启**才生效。
   这反而与周期性压缩 + reload 天然对齐：切换与重启合成一个动作，不必额外发明流程

audit 的「干净往返」与 gui 同源，都是**以最终审核结果为准**：一次审计给出了结论、没崩、没超时、没人叉掉窗口。

audit 的看门狗：连续失败或超时达到阈值 → 切回 stable 槽并提示「需要重启才生效」，然后通知一次。

## 5. 运行期崩溃：自动回退 + 通知（已定）

金丝雀管的是「上槽前」，这一节管「上槽之后」：

- 看门狗发现窗口进程崩了（异常退出、render-process-gone、连续无响应）→ 把 current 软链指回 previous，
  杀掉残留进程，然后**通知提督一次**（hub/IM 一句话，带上崩的是哪个版本、现场在哪）
- 门槛是**连续失败 3 次**（默认 3，可配）：用连续数而不是累计数，偶发一次失败不该攒成回退理由；
  中间干净一次就重新数。三条"不退"：没到门槛、已经在 previous 上（防套娃）、没有 previous 槽
- 判定与执行都放在共享的 noteRoundTrip 里，所以 CLI 手动记与 pi 侧自动记走的是同一套，不会两套行为
- 自动回退不改任何代码路径：它执行的就是第 2 节那段独立 shell
- 回退后候选的连续成功计数清零，且记入现场留档

## 6. 极端情况下的图形操作面（三层，从近到远）

1. **软链切回上一个稳定版本**——一段几十行的独立 shell，Electron 完全起不来时也能用
2. **TUI 兜底**——闸门已有 TUI 面板（不依赖 GUI 进程）
3. **IM 通道**——飞书适配器，本机闸门窗答不了时它接手

关键在第 1 层：它必须在「Electron 崩了」这个前提下可用，所以它不能住在 Electron 里，也不能住在 pi 扩展里。

## 7. 崩溃现场

候选失败时把这几样存到状态目录（按敏感内容对待，不进仓）：

- 当时的 request.json（能复现就有救）
- stderr / 退出码 / render-process-gone 详情
- 若是核心转储，记一条提示（coredump 路径）

## 8. 本稿范围之外

GUI 侧没有网络请求：文件协议、IPC、spawn 全在本地。所以「注入网络故障」这件事与本稿无关。

（审核 SDK 那边确实会调模型走 HTTP，但那是脚本侧的事，不在这里混着做。）

## 9. 分期

| 期 | 内容 | 完成标志 |
|---|---|---|
| 1 | 两槽 + 软链切换 + 独立回退脚本 | 手动换一次版本再切回来，全程不碰 Electron |
| 2 | 干净往返计数 + 上槽门槛（连续 N 次）+ --force 留痕 | 故意塞一个坏产物跑，计数永不达标、它拒绝上槽 |
| 2.5 | 运行期看门狗：崩了自动回退并通知 | 人为崩一次，软链指回去且收到提示 |
| 3 | 能力探测 + 缺能力降级 | 旧 GUI 配新 pi 跑通一次 |
| 4 | 崩溃现场保存 | 人为崩一次，日志与请求快照都落对地方 |


## 10. 硬约束

1. 切换与回退不依赖被切换的东西（软链 + 独立 shell）
2. 金丝雀失败绝不自动上槽、绝不自动重试
3. 协议不匹配只提示不拦——拦了就成了新的单点
4. 状态目录里的现场快照按敏感内容对待，不进仓
