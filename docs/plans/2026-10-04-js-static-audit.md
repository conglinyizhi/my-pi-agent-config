# run_code 的静态指令审计（JS 影响面分析）

2026-10-04。目标：让 `run_code` 脚本在**执行前**给出一份可靠的影响面（读哪些文件、写哪些文件、
调哪些工具、参数是什么），据此做一次审批；执行期保留越界拦截作为兜底。

## 1. 现状与缺口

`ptc.mode = only` 之后，模型只能写 `run_code` 脚本，其余工具从脚本里调。内层调用走的是
和直接调用**同一条**工具管线：`bash` 进 `bash-guard` 的审批链（`checkCommand` 自动判定 →
LLM 预审，`auto` 档判 safe 就静默放行 → 否则人工闸门），读写工具进 `guard.ts` 的路径判定。

三个缺口：

1. **批量连爆卡**：一段脚本发十条需要人工确认的命令，人一次吃十张卡
2. **审命令不审意图**：每条命令单独看，"这段程序为什么这么干"没人看。理由字段
   （`lib/ptc-reason.ts`）已经备好，但没有消费方
3. **外层零拦截**：JS 本身不经过任何判定，路径拼接、变量展开都发生在拦截之前

已有的零件：理由的消毒与登记（`lib/ptc-reason.ts`）、嵌套调用的 `parentToolCallId` 链、
`tool_call` 钩子（可 block）、审批卡与 LLM 预审缓存（`lib/bash-approval.ts`）。

## 2. 目标与不变量

- 执行前产出影响面，**一次**审批绑定一段程序；执行期越界即停
- 宁可误报不可漏报：漏报是安全洞，误报只是多问一次
- 报告只放事实，不放结论性文字（理由、代码片段、文件内容都是不可信文本，见 §7）
- 分析失败、超时、命中不可分析构造 → 按"信息不全"处理：默认要人批一次；**绝不静默放行**
- 批准绑定 `digest(脚本原文 + 摘要)`，脚本一改即失效

## 3. 三条事实来源

| 来源 | 时机 | 覆盖面 | 精度 | 用途 |
|---|---|---|---|---|
| AST 抽象解释 | 执行前 | 所有分支（含走不到的） | 值可能不精确（⊤） | 界定兜底边界（上界） |
| 干跑 dry-run | 执行前 | 真实控制流走过的那条 | 参数精确，但路径受假数据影响 | 审批卡上的"确定要做"（下界） |
| 真跑拦截 | 执行中 | 事实 | 精确 | 最终判定与审计 |

任何一层单独用都不成立：只有静态会漏掉动态构造，只有干跑会被假数据带偏，
只剩真跑一层，就等于退回现在的逐条弹卡。

## 4. 干跑（P1）

**不用改引擎**：引擎把每次内层调用交给 `ctx.executeTool`（`extensions/codemode/execute.js`），
所以干跑就是**换一个 ctx 再跑一次**。

要替换的 ctx 面：

- `executeTool`：记录 `(name, args)` 后返回占位结果，不真执行
- `modelRegistry`：`models.*` 不通（否则干跑真花 token）
- `sessionManager.getBranch()`：`load()` 读真值，`store()` 的写入丢弃（不能污染真跑）
- `tools`：**不换**，必须与真跑一致，否则脚本看到的工具面不同

已知失真（写进设计，不试图消除）：

- 控制流依赖读取结果时，干跑走的分支与真跑不同（`if (r.includes("x"))`）
- 脚本可能因为假数据抛异常 → 用已收集的调用作为**部分摘要**，并标注"干跑未跑完"
- 循环次数、`Math.random`、`Date.now` 造成的差异同样归入"下界"这个前提

成本：一次脚本执行（毫秒级），复用引擎既有的 `timeout_ms` 与 256MB 内存上限。

## 5. 静态分析（P2）

### 5.1 解析器

用 `typescript` 包的 `ts.createSourceFile`：零新依赖（仓库已有 typescript），容错解析，
JS/TS 都吃，AST API 完整。备选 `meriyah`/`acorn` 更快，但要新增依赖，先不引。

不追求完整符号执行：做**抽象解释**，够用且可控。

### 5.2 抽象解释

值域：`Bottom`（不可达）/ `Const(有限字符串集合)`（含前缀形式）/ `Unknown`（⊤）。

环境：作用域链 + 变量 → 抽象值；本脚本内定义的函数做内联（深度与次数设上限）。

转移规则要点：

- 字符串拼接与模板字面量：全部操作数是 Const 就折叠，出现 ⊤ 即结果为 ⊤
- 条件：两支都分析，出口做 join（并集）
- 循环：固定点迭代，轮数上限 + widening（超限即该变量升 ⊤，避免分析爆炸）
- 数组/对象：浅层建模（`Promise.all([a, b])` 逐个元素分析）
- 调用点识别：`tools.x(...)`、`tools["x"]`、别名（`const t = tools`）、解构（`const { read } = tools`），
  工具名是常量集就逐个展开，是 ⊤ 就标 unknown
- 工具返回值：默认 ⊤；不建模各工具的输出格式

### 5.3 不可分析构造

`eval`、`new Function`、`with`、动态工具名、超过迭代上限的循环 —— 命中任一条，
整个脚本标 `opaque`，强制走"真跑 + 逐条人工"，不享受"程序级批准"。

### 5.4 输出

```ts
interface EffectReport {
  reads:  PathEffect[];   // { path, certainty: "const" | "prefix" | "unknown", source: "static" | "dryrun" }
  writes: PathEffect[];   // 同上，另带 op: "create" | "modify" | "delete"
  calls:  CallSite[];     // { tool, args摘要, certainty, line }
  unknowns: UnknownSite[];// 推不出来的调用点（含行号）
  opaque: boolean;        // 命中不可分析构造
  complete: boolean;      // 干跑是否跑完
}
```

## 6. 审批与决策（P3）

卡片结构（沿用 audit 卡的样子，顺序固定）：

1. 理由（已消毒，一行）
2. 确定影响面：干跑得到的读 / 写 / 调用
3. 可能影响面：静态上界推出来的、干跑没走到的
4. 未知项：含 ⊤ 的调用点（行号 + 那段代码）
5. 脚本 digest 前 12 位

决策矩阵：

| 情况 | 处理 |
|---|---|
| **事前**（静态 + 干跑）发现越界，或命中硬拦 | **整段不执行**，返回编译失败式的错误（§6.2）。零副作用 |
| **事前**判定需要人 | 弹一次卡：批 → 整段执行；拒 → 同样返回那种错误 |
| **事前**判定通过（含批准表命中） | 整段执行，内层调用按批准范围放行，中途不再弹卡 |
| 真跑时出现摘要外的调用（前两层都漏了） | 立即停，返回失败 + 已执行清单；唯一带副作用的路径，审计里单列 |
| 命中黑名单 / 凭据 / 受保护路径 | 哪一层发现都直接拒，不受程序级批准影响 |
| `opaque` 或 `complete === false` | 不享受"程序级批准"，走 §6.2 的报错（`E-OPAQUE`） |

### 6.1 批准的生命周期与绑定

批的是什么、能活多久，比"越界停不停"更决定这套东西安不安全。主张：**批准绑事实，不绑上下文**。

一条批准记录：

```ts
interface Grant {
  scope: { scriptDigest: string; paths: string[]; tools: string[] };
  targetHashes: Record<string, string>;  // 路径 → 批准时该文件的内容 hash（不存在记 "absent"）
  expires: "session";                    // 目前只有这一档
  kind: "read" | "write";
}
```

- 判定时**重算**目标文件的 hash：没变且在窗口内才放行；变了即失效、重新问。判定输入永远是当场算出的事实，
  不是任何模型或人对文件系统的记忆 —— 于是"上下文脱离之后谁保证了解还准"这个问题不存在
- 先例：MCP 编辑工具的 `viewed_code_id`（读它时这个范围长这样），同一思路

分档（不做"一律问"或"一律放"）：

| 档 | 范围 | 批准 |
|---|---|---|
| 不可逆 / 跨边界 | 删除、写工作区外、凭据、网络外传 | 每次都问，不入批准表 |
| 可逆 | 读、工作区内写、`/tmp` | 按事实 + hash 复用，不再打扰人 |

模型的位置：**只免除上报，不授予权限**。快模型（Jev 形态的 classifier）做高频过滤，chat 模型做低频审读，
`chain` 的合并保持保守（任一判风险就上报）——这三样现成（`extensions/sandbox-permissions/llm-review.ts`
的 `backend: chain`）。授权永远归人，于是"模型上下文有限"影响不了授权，只可能让某个本可上报的问题没上报，
而 hash 绑定兜住"事实变了"的那一半。

不选"一律问"的理由是审批疲劳：每次都问，人会闭眼点同意，那时候漏批比省事更危险。

与现有链的关系：内层命令的自动判定与硬拦**不变**；变化只发生在"要不要弹人工闸门"这一步。
bash 的 capability / network 审批链不动。

### 6.2 越界 = 整段废弃（已定）

命中越界或硬拦时**不执行整段脚本**，像编译失败那样返回：零副作用、一条结构化错误、模型自己改再发。

这么选的三个理由：

- **语义干净**：不必定义"执行到一半停下来"这种状态（已执行的调用不回滚，模型重试会把副作用做第二遍）
- **成本更低**：判定放在执行前，一次算清。执行中反复"暂停 → 问 → 继续"每一轮都是新的模型请求，
  工具结果进对话还会改前缀、掉缓存；输入多一点比多跑几轮输出便宜得多（决策口径：缓存命中便宜，
  输出比输入贵数倍）
- **形态命中训练数据**：编译器/构建器的报错是模型见得最多的失败形态，"报错 → 改 → 重发"是它熟悉的循环

报错形状照编译器那套来：位置 + 原因 + 规则 + 可行动作。

```
run_code: 本段未执行（安全审核未通过）
  script.js:12:5  E-OVERSCOPE  写入路径超出批准范围：/etc/hosts
  script.js:24:3  E-EVAL      用了 eval，无法静态分析
为防止副作用，整段脚本被丢弃：没有产生任何读写。

修好这几处再发一次；确实需要越界的能力，就把需求报给主 agent。
```

错误码：`E-OVERSCOPE`（越界）/ `E-EVAL`（不可分析构造）/ `E-DENIED`（人拒绝，或命中硬拦项）/
`E-STALE`（批准因目标文件已变而失效）。

两条约束：

- 报错里回显的路径与代码片段同样过一遍 §7 的消毒（它们是不可信文本）
- 只有**事前**拦得住"零副作用"。真跑漏网那一条（前两层都没预测到的调用）只能"立即停 + 把事实交给人"，
  那时副作用已经发生，审计里必须单独标出，别和事前废弃混为一谈

## 7. 注入与消毒

报告里每个字段都是不可信文本：路径、文件名、要写入的内容、命令原文、理由本身。

- 消毒复用 `lib/ptc-reason.ts` 的 `sanitizeExecutionReason`：控制字符与换行压单行、
  尖括号换全角、长度封顶
- 路径另外要 canonicalize：去 `..`、解软链、剥 `U+202E` 这类双向控制符
  （它能让 `evil.txt` 显示成 `txt.live`，专门骗看文件名的人）
- 卡片正文只放结构与事实；内容片段（写文件的内容、命令原文）进可展开的数据区，标注来源
- **干跑天然抗一类注入**：摘要里的参数是脚本按假数据构造的，从文件/网页读到的攻击者内容
  根本没进来。真跑那一步的越界判定才需要正面处理注入

## 8. 折叠与展示

公共父目录折叠只在"同一父目录下条目数 ≥ 阈值"时做，且：

- 命中黑名单 / 凭据类的叶子**永不折叠**
- 删除类操作、写工作区外的操作不折叠
- 折叠后仍给出条目数与展开入口

## 8.1 审计与批准记录的存储

**全部放内存，按条数滚动，不落盘**（磁盘寿命考虑，见 2026-10-04 的决定）。

- 于是"批准的生命周期 = 本会话"天然成立，不用另立规则；重启即忘，语义干净
- compaction、fork 这类"对话上下文变了但进程还在"的情况，批准照旧有效（绑的是事实，不是对话）
- 已认下的代价：事后只能回看最近 N 条，取证能力有限

## 9. 性能与降级

预算：解析 + 静态分析 < 100ms（脚本通常几 KB）。

降级**不改变"事前一次判定"这个形态**（§6.2 的零副作用依赖它），只改变判定的依据强度：

`静态 + 干跑都有` → 静态超预算就只信 `干跑` → 干跑也超时/异常，就按"信息不全"处理：
**默认要人批一次**（而不是默认放行）。人批 → 整段执行；人拒 → 整段废弃。

每一级退化都要在卡片上说明原因，不静默。

## 10. 边界（明确不做）

- **bash 命令内部不做 JS 级分析**：shell 的动态性（`$(...)`、变量展开）留给 preshell/tokenize 那套；
  摘要里 bash 先按"不透明命令原文"列出来给人看
- 不做完备符号执行，不追求"证明性地完备"
- 不接管模型直接发起的工具调用（那是现有链的事）

## 11. 分阶段

| 阶段 | 做什么 | 验收 |
|---|---|---|
| P0 观测 | 真跑时把每次 `run_code` 的调用序列、理由、脚本原文落审计，不做任何拦截 | 跑一周真会话，攒出语料；审计条目不丢调用 |
| P1 干跑 | ctx stub + 调用聚合 + 摘要生成，仍不拦截 | 干跑输出与真跑调用做一致性对比，差异必须能解释（假数据分支） |
| P2 静态 | AST 抽象解释，输出 EffectReport | 语料上的"不漏报"断言通过（见 §12） |
| P3 决策 | 摘要进审批卡；越界即停；digest 绑定与失效 | 一次脚本只弹一次卡；越界必停；脚本改一处即失去批准 |
| P4 打磨 | 折叠、消毒规则、性能预算、降级提示 | 预算内完成；注入样例不改变卡片语义 |

## 12. 语料与测试

- 语料脚本：正常批处理、模板拼接、循环生成调用、别名与解构、`Promise.all`、
  `eval`、动态工具名、读文件后当路径、混淆变体（`String.fromCharCode` 等）
- 断言方向：**不漏报**（误报可接受）。用"真跑出现的每个调用，必须落在
  `静态 ∪ 干跑 ∪ 未知 ∪ opaque` 里"做一致性断言，任何静默漏掉即测试失败
- 三源差异必须落在"未知/越界"这一类上，不允许静默丢弃
